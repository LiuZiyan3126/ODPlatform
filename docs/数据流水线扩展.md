## 1. split_mode 是否划分 扩展
本次扩展为数据集转换流程新增了“保留原有数据划分”的能力，目标是兼容 Roboflow 等已经按 `train/valid/test` 划分好的数据集，避免在转换格式时重新随机划分，从而保留原始数据隔离关系和评估语义。原有流程保持不变，仍然是默认的 `resplit` 模式，即读取 `data/raw/<dataset>/images` 和 `data/raw/<dataset>/annotations`，先统一转换为 YOLO 标签，再通过已有 split strategy 重新划分为 `train/val/test`。新增的 `preserve` 模式则读取 `data/raw/<dataset>/train`、`valid|val|validation`、`test` 目录，分别对每个 split 内的标注进行格式转换，并直接构造 `SplitManifest(train, val, test)`，最后复用现有的 `materialize()` 和 `write_dataset_yaml()` 输出到标准的 `data/processed/<dataset>/train|val|test` 结构。

代码层面，在 `common/constants.py` 中新增了 `SplitMode` 常量类，定义 `RESPLIT = "resplit"` 和 `PRESERVE = "preserve"`，并增加 `DEFAULT_SPLIT_MODE = SplitMode.RESPLIT`，保证旧命令默认行为不变。在 `cli/transform_data.py` 中新增了 `--split-mode {resplit,preserve}` 参数，其中 `resplit` 表示转换后重新划分，`preserve` 表示保留已有划分，只做格式转换。在 `data_pipeline/orchestrator.py` 中，`DatasetPipeline.run()` 被拆分为两条流程：`_run_resplit()` 承载原有逻辑，`_run_preserve_split()` 承载新增逻辑；同时新增了 split 目录发现、preserve 模式预检、类别解析和指定图片目录配对等辅助方法。

新增 preserve 流程支持将常见目录名标准化：`train` 映射为平台的 `train`，`val`、`valid`、`validation` 映射为平台的 `val`，`test` 映射为平台的 `test`。其中 `train` 和 `val` 是必要划分，`test` 可被识别并保留。对于 Pascal VOC 和 COCO，如果用户未显式传入 `--classes`，系统会从所有 split 的标注中扫描类别并生成统一类别表；对于 YOLO 格式，由于标签文件只包含数字类别 id，不包含类别名，因此在 `preserve + yolo` 模式下必须显式提供 `--classes`，以保证生成的 dataset yaml 中 `names` 与标签 id 对齐。

本次设计没有新增 split mode 注册表，因为当前 split mode 只有两类大流程：未划分数据重新划分，以及已划分数据保留结构。它们更像 pipeline 层面的流程分支，而不是普通的 split strategy。现有 `strategy_registry.py` 继续只负责 `resplit` 模式下“如何划分一批样本”，例如 random、stratified 等策略；新增的 `preserve` 模式则绕过重新划分策略，直接从已有目录结构构造 `SplitManifest`。这样能保持架构语义清晰：`split_mode` 决定是否保留已有划分，`split_strategy` 只决定重新划分时采用什么策略。

典型使用方式如下：

```powershell
odp-transform --dataset fire --format pascal_voc --task detect --split-mode preserve --classes fire hunman-fire
```

该命令会读取：

```text
data/raw/fire/train
data/raw/fire/valid
data/raw/fire/test
```

并输出为平台标准结构：

```text
data/processed/fire/train/images
data/processed/fire/train/labels
data/processed/fire/val/images
data/processed/fire/val/labels
data/processed/fire/test/images
data/processed/fire/test/labels
```

同时生成：

```text
apps/platform/configs/datasets/fire.yaml
```

验证方面，已完成 Python 编译检查，`odp-transform --help` 能正常显示新增的 `--split-mode` 参数，并对 `fire` 数据集进行了只读预检，系统能够识别 `train -> train`、`valid -> val`、`test -> test`，并发现类别 `hunman-fire` 和 `fire`。

## 2. split_strategy 数据划分策略扩展

本次扩展在原有 `random` 随机划分的基础上，新增了 `stratified`、`stratified_multilabel` 和 `hash` 三种数据划分策略，分别解决单类别分层、多类别联合平衡和增量数据稳定划分三个问题。三种策略均沿用现有 split strategy 注册表机制：每个策略作为独立模块放在 `data_pipeline/split/strategies/` 目录下，通过 `@register_strategy` 装饰器完成注册；注册表首次使用时会自动扫描并导入该目录中的策略模块，因此 `split_service.py` 和 `orchestrator.py` 不需要针对每种策略增加条件分支，仍然通过统一的 `split_pairs()` 接口传入样本、比例、随机种子和标签信息，并统一返回 `SplitManifest(train, val, test)`。

`stratified` 是单标签分层策略。目标检测图片可能同时包含多个类别，因此该策略会先对每张图片的类别列表去重，再统计各类别在整个数据集中的图片出现频率，并选择图片中全局最稀有的类别作为该图片的代表类别；没有目标的纯背景图片会进入独立的 `__background__` 层。完成分层后，策略优先处理样本较少的层，并在 `train/val/test` 的剩余容量约束下分配图片，使各代表类别尽量按照目标比例分布。该策略实现简单、速度快，并且严格满足当前 `three_way_counts()` 计算出的集合容量，但一张图片只能选择一个代表类别，因此不能同时保证图片中所有次要类别的分布。

`stratified_multilabel` 是面向目标检测数据的多标签分层策略。它不会把一张图片压缩成单个代表类别，而是保留图片包含的全部类别，并采用稀有标签优先的迭代分配方式：每轮先找到剩余图片中出现次数最少的类别，再从包含该类别的图片中选择待分配样本，计算 `train/val/test` 对该稀有类别以及图片内其他类别的目标缺口，最后把图片放入类别缺口最大且仍有容量的集合。每完成一次分配，策略都会同步更新集合剩余容量和各类别已分配数量。该方法能够同时照顾主要类别与次要类别，比普通随机划分和单标签分层更适合一张图片包含多个目标类别的数据集；同时它仍然严格满足集合总容量，但当某个类别样本极少、类别高度绑定或目标比例无法整除时，只能尽量接近目标分布，无法凭空保证每个类别都出现在三个集合中。

`hash` 是稳定哈希划分策略。该策略不会先打乱全部样本，而是使用 `random_state` 和图片文件名组成稳定样本标识，通过 BLAKE2b 计算哈希值，再把哈希值映射到 `[0, 1)` 区间：小于 `train_rate` 的样本进入 `train`，位于 `train_rate` 和 `train_rate + val_rate` 之间的样本进入 `val`，其余样本进入 `test`。由于每张图片的归属只取决于自身文件名和随机种子，后续向数据集中追加新图片时，已有图片不会因为重新排序或重新洗牌而改变所属集合，适合持续采集、持续训练和数据集版本迭代场景。该策略使用文件名而不是绝对路径，因此数据集整体搬迁后仍能保持划分结果；但文件名必须保持稳定且不能重复。与另外两种策略不同，`hash` 不保证精确的集合数量，也不主动平衡类别，只能在样本数量较大时使实际比例统计上接近目标比例。

代码层面，在 `common/constants.py` 的 `SplitStrategy` 中补充了 `HASH = "hash"`，并将其加入 `SplitStrategy.all()`，因此 CLI 的 `--split-strategy` 参数现在支持 `random`、`stratified`、`stratified_multilabel` 和 `hash`。在 `data_pipeline/split/strategies/` 中新增了 `stratified_split.py`、`stratified_multilabel.py` 和 `hash_split.py`：其中两个分层策略使用 `requires_labels=True` 声明必须提供 `labels_per_image`，如果上游没有传入每张图片的类别列表，`split_service.py` 会在调用策略前直接报错；`hash` 不依赖标注内容，因此使用 `requires_labels=False`，可以只根据样本文件名完成划分。

典型使用方式如下：

```powershell
# 单标签分层：使用每张图片中全局最稀有的类别作为代表类别
odp-transform --dataset fire --format pascal_voc --task detect --split-strategy stratified

# 多标签分层：同时平衡一张图片包含的全部类别
odp-transform --dataset fire --format pascal_voc --task detect --split-strategy stratified_multilabel

# 稳定哈希：追加新数据时保持已有图片的集合归属
odp-transform --dataset fire --format pascal_voc --task detect --split-strategy hash --seed 1210
```

三种策略均支持通过 `--train-rate` 和 `--val-rate` 指定比例，`test_rate` 由 `1 - train_rate - val_rate` 自动计算；比例越界时会复用 `_common.py` 中的 `validate_rates()` 直接终止。`stratified` 和 `stratified_multilabel` 使用 `--seed` 处理同分候选和样本顺序，在输入样本顺序发生变化时仍可复现相同划分；`hash` 则把 seed 作为哈希输入的一部分，相同文件名和 seed 会得到固定归属，修改 seed 会生成另一套稳定划分。

验证方面，新增了 `tests/test_split_strategies.py`，覆盖策略自动发现、分层容量、类别分布、多标签平衡、输入顺序无关的可复现性、哈希增量稳定性、哈希大样本比例和非法比例校验。当前运行环境未安装项目开发依赖 `pytest`，因此没有直接执行 pytest 命令，但已使用标准库执行等价性质检查，并完成 Python 编译检查以及 `0～100` 个样本、多种划分比例、纯背景图片和零容量子集的边界扫描。全部检查通过；在 5000 个样本、目标比例为 `80%/10%/10%` 的哈希测试中，实际结果为 `80.42%/10.00%/9.58%`，符合稳定哈希策略的近似比例特性。`odp-transform --help` 也能够正常显示 `--split-strategy {random,stratified,stratified_multilabel,hash}`。

## 3. 划分后数据指纹扩展

本次扩展为数据转换与划分结果增加了数据指纹，并将指纹直接记录在现有 dataset YAML 的 `odp_meta.fingerprint` 中。数据指纹的目标不是替代数据文件，而是为一次确定的数据集版本生成稳定身份标识：训练、验证或问题追踪时，只要对比 YAML 中的总指纹，就能快速判断使用的数据内容、类别语义和 `train/val/test` 划分是否完全一致。此次没有额外生成 CSV，因为当前需求主要是标识整份数据集版本，YAML 本身又会作为训练入口长期保存，把指纹与数据路径、类别表和划分元数据放在一起更不容易丢失或错配；如果后续需要逐文件审计，再基于同一指纹模块扩展 CSV 清单即可。

指纹采用 SHA-256 计算，并覆盖四类信息：类别名称及其索引顺序、每个样本所属的 `train/val/test`、图片与标签文件名、图片与标签文件内容。类别顺序必须参与指纹，因为 YOLO 标签中的数字 class id 只有结合 `names` 才有真实语义；split 归属必须参与指纹，因为相同文件被放入不同集合时代表不同的训练和评估数据；文件内容参与指纹后，即使文件名不变，只要图片或标签被修改，指纹也会变化。绝对路径和生成时间不会参与计算，因此数据集整体搬迁到其他目录后仍可得到相同指纹，重复执行相同转换和划分也不会因为运行时间不同而产生新指纹。

代码层面，在 `data_pipeline/split/fingerprint.py` 中新增了统一的指纹构建逻辑。每个文件以分块方式读取并计算 SHA-256，避免把大图片一次性加载进内存；每条哈希输入使用长度前缀进行编码，避免多个字段直接拼接产生边界歧义。模块会先分别计算 `train`、`val` 和 `test` 子指纹，再把三个子指纹与类别表组合成数据集总指纹。子指纹可以帮助定位是哪一个 split 发生变化，总指纹则用于快速比较整份数据集。记录顺序经过排序，因此 manifest 内部样本顺序变化不会影响结果。

`data_pipeline/split/yaml_writer.py` 会在写 YAML 前调用 `build_dataset_fingerprint()`，因此 `resplit` 和 `preserve` 两条流程都会自动生成指纹，不需要在 `orchestrator.py` 中增加重复分支。`odp_meta.schema_version` 由 `1` 升级为 `2`，表示元数据结构新增了 fingerprint 字段；原有的 YOLO 标准字段 `path`、`train`、`val`、`test`、`names` 和 `nc` 均保持不变，训练框架可以继续正常读取。

生成的 YAML 结构示例如下：

```yaml
odp_meta:
  schema_version: 2
  dataset_name: fire
  source_format: pascal_voc
  task: detect
  fingerprint:
    algorithm: sha256
    version: 1
    scope: classes+split_assignment+file_names+file_contents
    value: d241c4d2315564d1bef59b9973460214c9b4cda69e8e5fb35f1b9a50c380220a
    splits:
      train:
        value: c89003e6faeffbf3602711bc08932d317afce3ccbcd69826adb1ae9b6c0b94a5
        samples: 1
      val:
        value: 1dafa30b43828091f1a28ea9366e8c50f0891ec145fb43c00ec848ddb6a275c4
        samples: 1
      test:
        value: 96f2d432cfe19d1080b4595cc8d977dfb32d0e3a3eff8d532488a7d4a1029d97
        samples: 0
```

其中 `algorithm` 表示摘要算法，`version` 表示指纹计算规则版本，`scope` 明确说明当前指纹覆盖范围，顶层 `value` 是整份数据集的总指纹；每个 split 下的 `value` 是该集合的子指纹，`samples` 是参与计算的图片—标签对数量。后续如果修改指纹规则，应提升 fingerprint 自身的 `version`，使新旧算法生成的结果不会被误认为可直接比较。

验证方面，新增了 `tests/test_dataset_fingerprint.py`，覆盖路径无关性、文件内容变化、split 归属变化、类别顺序变化和 YAML 字段写入。Python 编译检查和标准库等价测试均已通过：相同文件复制到不同目录后指纹保持一致；修改标签内容、把样本从 `val` 移到 `train`，或者交换类别顺序时，总指纹都会变化；生成的 YAML 能正确写入 64 位十六进制 SHA-256 总指纹、三个 split 子指纹及对应样本数。由于计算范围包含图片和标签全部内容，生成 YAML 时会额外顺序读取一次数据集文件，这是获得内容级可追溯性的预期开销。

## 4. 数据质检项扩展

本次扩展在原有 `yaml_schema`、`pair_existence`、`label_format` 和 `split_uniqueness` 四项有效检测基础上，新增了 `orphan_labels`、`empty_labels`、`image_integrity`、`annotation_geometry` 和 `fingerprint_integrity` 五项检测。所有新增检测均作为独立模块放在 `validate_dataset/checks/` 目录，通过 `@check` 装饰器注册，并由现有自动发现机制加载，因此 `service.py` 的调度逻辑不需要增加检查项分支。运行 `odp-validate` 时，现在会自动执行九项真实数据检测以及一项用于验证注册机制的“冒烟测试”。

`orphan_labels` 用于检查“有标签、无图片”的孤儿标签。检测会根据 dataset YAML 中每个 split 的图片目录推导同级 `labels` 目录，扫描其中全部 `.txt`，并将标签 stem 与对应 split 的图片 stem 进行比较。没有孤儿标签时返回 PASS；孤儿比例低于 `LABEL_ORPHAN_WARN_RATIO = 10%` 时返回 INFO；达到或超过 10% 时返回 WARNING。孤儿标签通常不会直接进入训练，但可能意味着图片丢失、文件命名错误或数据清理不完整，因此作为数据卫生问题报告，不直接升级为 ERROR。

`empty_labels` 用于统计已经与图片配对、但内容为空或只有空白字符的标签文件。空 YOLO 标签本身是合法的，通常代表没有目标的背景图片，因此检测不会将单个空标签视为格式错误：没有空标签时返回 PASS；空标签比例低于 `EMPTY_LABEL_WARN_RATIO = 20%` 时返回 INFO；达到或超过 20% 时返回 WARNING。报告会记录总标签数、空标签数量、各 split 数量和部分文件示例，帮助判断背景样本比例是否符合数据采集预期。

`image_integrity` 使用 Pillow 对每张图片先执行格式完整性验证，再实际加载像素数据，以发现损坏、截断、伪造扩展名或无法解码的图片。全部图片可解码时返回 PASS，只要发现一张无法解码的图片就返回 ERROR，因为训练过程可能在加载该批次时直接失败。为了避免可选环境依赖导致整个注册表加载失败，Pillow 在检查函数内部按需导入；如果运行环境没有安装 Pillow，该项返回 INFO 并明确说明跳过原因。

`annotation_geometry` 在 `label_format` 的结构和数值范围检查之外，进一步验证标注是否形成有效几何形状。对于 detect 标签，它检查框的宽高必须大于零，并根据中心点和宽高还原边界，确认框没有超出归一化图片范围；边界比较保留 `1e-6` 浮点容差，避免正常的小数舍入误报。对于 segment 标签，它使用鞋带公式计算多边形面积，检查所有点重合或共线导致的零面积多边形。格式本身不合法的行仍交给 `label_format` 报告；格式正确但几何无效的标注由本项返回 ERROR。

`fingerprint_integrity` 会重新计算当前 processed 数据集的 SHA-256 指纹，并与 dataset YAML 中 `odp_meta.fingerprint` 记录的总指纹和 split 子指纹比较。完全一致时返回 PASS；图片、标签、类别顺序或 split 归属发生变化时返回 ERROR，并在可以定位时列出发生变化的 split；如果有标签缺失，指纹无法完整重算，也返回 ERROR。为了兼容指纹功能加入前生成的旧 YAML，没有 fingerprint 字段时只返回 INFO，不会阻止旧数据集继续质检。

本次同时修正了 snapshot 的任务类型解析：旧逻辑只读取 YAML 顶层的 `task`，而当前 `write_dataset_yaml()` 将任务类型记录在 `odp_meta.task`，导致未显式传参时 segment 数据可能被按 detect 检查。现在解析顺序为命令行 `task_type`、YAML 顶层 `task`、`odp_meta.task`、默认 `detect`，既兼容旧结构，也能正确识别当前生成的分割数据集。此外移除了 `yaml_schema.py` 中未使用的 Polars 导入，避免一个基础 YAML 检查无故依赖 Polars。

新增检测的严重级别汇总如下：

| 检测项 | PASS | INFO | WARNING | ERROR |
|---|---|---|---|---|
| `orphan_labels` | 无孤儿标签 | 比例低于 10% | 比例达到 10% | 不使用 |
| `empty_labels` | 无空标签 | 比例低于 20% | 比例达到 20% | 不使用 |
| `image_integrity` | 全部可解码 | Pillow 不可用 | 不使用 | 任意图片损坏 |
| `annotation_geometry` | 全部几何合法 | 不使用 | 不使用 | 任意非法框或多边形 |
| `fingerprint_integrity` | 指纹一致 | 旧 YAML 未记录指纹 | 不使用 | 指纹不一致或输入缺失 |

## 5. 问题 CSV 与 HTML 质检报告扩展

本次扩展将一次质检的落盘产物从单一 `report.json` 升级为完整报告包。正常运行 `odp-validate` 后，同一个 `runs/data_validation/<run_id>/` 目录现在会同时生成 `report.json`、`issues.csv` 和 `report.html`：JSON 保留完整的机器可读检测结果，CSV 按问题逐行记录需要处理的数据，HTML 则提供可以直接在浏览器中阅读和交付的可视化报告。原有 `--no-report` 参数仍然有效，但语义调整为同时禁止 JSON、CSV 和 HTML 三种产物，只执行检查并输出终端日志。

为了保证 CSV 不是只有少量示例，本次同步扩展了各检查项的结构化 `details`。`pair_existence`、`orphan_labels` 和 `empty_labels` 会保留按 split 分类的完整文件列表；`label_format`、`annotation_geometry` 和 `image_integrity` 会保留全部逐文件错误，同时继续提供截断后的 preview 给终端日志使用；`split_uniqueness` 会保留完整的重复 stem 列表。这样终端不会被大量问题刷屏，但 CSV 和 HTML 可以覆盖全部已发现的问题数据，而不是只导出前 10～20 条。

新增的 `validate_dataset/artifacts.py` 负责把不同检查项的 details 统一转换为 `IssueRecord`，其稳定字段包括：

| 字段 | 含义 |
|---|---|
| `check_name` | 发现问题的检测项 |
| `severity` | `INFO/WARNING/ERROR` 严重级别 |
| `split` | 问题所属的 train、val、test 或重叠 split |
| `file` | 图片、标签路径或重复样本 stem |
| `line` | 标签文件中的错误行号，没有则为空 |

| `recommendation` | 面向用户的修复建议 |

HTML 报告为单文件、自包含页面，不依赖 CDN、JavaScript 框架或额外静态资源。报告顶部展示运行编号、总体严重级别和耗时，随后以统计卡展示 PASS、INFO、WARNING、ERROR 数量，并包含数据集基本信息、各 split 图片与实例摘要、全部检测项结果、逐问题数据和修复建议。问题表支持横向滚动和固定高度滚动，适合问题数量较多的数据集；页面使用响应式布局，在窄屏上会自动调整统计卡和元数据列数。所有来自文件名、错误详情和数据集配置的文本在进入 HTML 前都会转义，避免异常数据破坏页面结构。

## 6. Pascal VOC 坐标转换修正

在使用 `annotation_geometry` 检查 fire 数据集时，共发现 5210 个标注中有 345 个框超出图片边界。进一步核对报告、处理后的 YOLO 标签、图片尺寸和原始 XML 后确认，这 345 个错误全部不是随机脏数据：其中 174 个满足 `xmax = image_width + 1`，141 个满足 `ymax = image_height + 1`，另有 30 个同时满足两种情况，没有零宽、零高或超过一个像素以上的异常。对于 640×640 图片，报告中的典型边界为 `1.0015625 = 1 + 1/640`；对于 256、224、352 等尺寸，越界幅度也分别等于一个像素的归一化比例。

根因是 Pascal VOC 使用从 1 开始的像素坐标，而原有 `convert_voc()` 直接把 XML 中的 `xmin/ymin/xmax/ymax` 除以图片宽高，没有转换为 0-based 坐标。Roboflow 导出的贴右边界或下边界标注可能写成 `W+1/H+1`，因此转换后会得到大于 1 的 YOLO 边界。`label_format` 只验证 `cx/cy/w/h` 每个字段是否单独位于 `[0,1]`，这些标签仍可能通过；`annotation_geometry` 会进一步还原 `left/top/right/bottom`，所以能够发现组合后的真实越界。

本次在 `data_pipeline/convert/converters/pascal_voc.py` 中新增 `_voc_box_to_yolo()`，转换时先将 VOC 四条边减 1，恢复为 0-based 坐标，再把边界裁剪到 `[0,W] × [0,H]`，最后计算 YOLO 的归一化中心点、宽和高。裁剪用于防御源标注本身存在负坐标或超过图片范围的情况；如果裁剪后宽或高不再大于零，该框不会写入 YOLO 标签，并输出包含 XML 文件名、类别和原始 bbox 的 WARNING。类别探测也调整到有效框确认之后，避免只有无效框的类别被错误写入类别表。

修正后的核心换算语义如下：

```python
x1 = clip(xmin - 1, 0, W)
y1 = clip(ymin - 1, 0, H)
x2 = clip(xmax - 1, 0, W)
y2 = clip(ymax - 1, 0, H)

cx = (x1 + x2) / 2 / W
cy = (y1 + y2) / 2 / H
w = (x2 - x1) / W
h = (y2 - y1) / H
```

新增 `tests/test_pascal_voc_converter.py` 覆盖三类场景：VOC 的 `641` 边界能够正确映射到 640 像素图片的归一化边界 `1.0`；真实越界框会被裁剪到图片范围；完全落在图片外、裁剪后退化的框会被拒绝。三个转换器测试均已通过。此外对 fire 的 train、valid、test 全部 5210 个 XML 框进行了只读全量扫描，使用新转换规则生成六位小数 YOLO 坐标后再次调用 `annotation_geometry`，最终结果为 `5210 valid / 0 invalid`。

代码修正不会自动改写已经生成的 `data/processed/fire`。需要重新运行 `odp-transform` 生成标签和新数据指纹，再运行 `odp-validate` 生成新的 JSON、CSV 和 HTML 报告；旧报告仍然描述修正前的数据版本，应当作为历史记录保留。
