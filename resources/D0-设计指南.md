## 一、我们要做的是什么

我们要做的,是一个**目标检测平台**。

先把"目标检测"说清楚。它是计算机视觉中的一类任务——在图像中**定位并分类**多个目标,一句话:**"图里有什么,在哪里。"** 它只是视觉任务谱系里的一类。常见任务及其**输出形态**:

- **图像分类(Classification)**:对整张图输出**单一类别标签**及置信度,不涉及位置。最基础的视觉任务。
- **目标检测(Object Detection)**:在一张图中定位多个目标,每个目标输出一组「**类别 + 边界框(bounding box)+ 置信度**」,同时回答"是什么"和"在哪里"——**本平台聚焦于此**。
- **图像分割(Segmentation)**:输出**像素级**结果而非框。又分**语义分割**(逐像素分类,不区分同类个体)与**实例分割**(在语义分割之上再区分同类的不同实例)。
- **姿态估计(Pose Estimation)**:定位目标上预定义的**关键点(keypoints)**并恢复结构,典型如人体骨架。
- **目标跟踪(Tracking)**:在**视频序列**中为同一目标维持跨帧一致的身份(track ID),通常建在检测之上。

![常见视觉任务:同一画面,五类任务的输出各不相同](./image/tasks-overview.png)

*同一画面,五类视觉任务给出的输出形态各不相同;本平台聚焦其中的目标检测。*

这些任务在**算法层面**高度同源:大多共享同一类**骨干网络(backbone)**做特征提取,仅在输出头(head)与损失函数上分化;你即将用到的 YOLO 系列,一套框架就同时覆盖检测、分割、分类与姿态。

而更值得注意的是**工程层面**。把"检测"换成"分割""分类",**算法的输出头变了,但它周围那一圈工程没怎么变**:数据怎么接入与标准化、超参数怎么管、训练产物怎么归档、推理怎么提速、输入源怎么切换——这些活,每类任务都得干一遍。

(要说"完全一样"是夸张了——分割的标注格式、评估指标和检测并不相同。但**链路的形状**是复用的:总是"读进数据 → 标准化 → 训练 → 评估 → 推理",变的只是每一环里塞的具体算法。)

所以这就是我们要做的事:不是写"一个检测脚本",而是**把每类视觉任务都无法回避的那套工程能力,一次性沉淀、长期复用**——这正是"平台"二字的含义。本次落地的任务是目标检测,平台命名为 **ODPlatform**;但它的工程结构对分割、分类等任务同样适用,无需改动——它在设计上就不与具体任务或具体数据集耦合。

> **算法是可替换的变量,工程链路是稳定的常量。**

那这件事,具体怎么做?

## 二、这件事通常怎么做

完整地做一个目标检测系统,是一条链:**准备并标注数据 → 训练模型 → 评估指标 → 用模型推理。** 这条链,正是本平台后面要一步步搭起来的东西。

但如果只是想最直接地"把它用起来"——拿一个别人已经训练好的模型,喂一张图,得到框——其实非常简单。简单到什么程度?自己跑一遍就知道。

装一个库:

```bash
pip install ultralytics
```

写下面这段(真正调用模型就几行,后面几行是顺手做的自测),存成 `detect_demo.py`:

```python
from ultralytics import YOLO

model = YOLO("yolo11n.pt")            # 第一次运行自动下载,最小的模型,约 5 MB
results = model.predict(
    source="https://ultralytics.com/images/bus.jpg",  # 官方示例图,自动下载
    save=True,                        # 把画好框的结果图存下来
)

# 顺手做个最朴素的"测试":确认它确实检测到了东西
boxes = results[0].boxes
print(f"检测到 {len(boxes)} 个目标")
assert len(boxes) >= 1, "一个目标都没检测到——检查环境或模型是否正确加载"
print("通过 ✅  结果图已存到 runs/detect/predict/ 下,打开看看")
```

跑它:

```bash
python detect_demo.py
```

你会看到类似:

```
检测到 6 个目标
通过 ✅  结果图已存到 runs/detect/predict/ 下,打开看看
```

(具体数字会随模型版本略有不同,正常。)打开那张结果图,公交车和几个行人都被框了出来,各自标着类别和置信度。

**一段能跑、还能自我验证的目标检测程序——就这么多。**

## 三、在这个时代,这件事已经简单到什么程度

现在停下来,看看刚才那件事有多容易:**十来行代码、五分钟、零 YOLO 内部知识(真正调用模型的核心就那么几行)。**

你甚至不必自己写。把"用 YOLO 写个目标检测脚本"丢给任意一个 AI 编程助手,十秒就能拿到同样的东西;照着官方文档抄,也是这一段。

换句话说——**"写出一个能跑的目标检测程序"这件事,今天已经几乎免费了。** 几年前它还是一道作业题,现在是一次复制粘贴。

那么问题来了:如果"能跑"已经这么便宜,**真正难的、真正值钱的,究竟是什么?**

先别急着下结论。我们把刚才那段代码,往真实场景里推一步看看。

## 四、往真实里推,它就开始撑不住

**先把输入从示例图换成你的摄像头。** 把 `source` 改成 `0`(默认摄像头),它能跑。但你拿的要是一台 720p、90fps 的工业相机呢?你想指定分辨率、帧率、采集后端(MSMF / DShow / V4L2)、编解码格式(codec)——`predict(source=...)` 根本不接受这些参数。它只读取属性,不允许设置。

**再把输入换成别的形态。** 这次是一条 RTSP 网络流;下次是一个 `.mp4` 文件;再下次是一整个装满图片的文件夹。每换一种,你都得自己重写读取循环、处理它们各自的边界情况。

**接着,你想从视频的第 2 小时 30 分开始处理。** 原生接口不支持随机定位(seek)——你只能从头读起。

**最后,你去翻 GitHub issue,找到一个能配分辨率的偏方:它教你手改第三方库的源码。** 你照做、跑通,然后某天 `pip install -U ultralytics`,改动被覆盖,一切打回原形。

停一下,看看刚才这一连串墙——它们没有一个是"算法问题"。模型一行没动,mAP 一分没掉。卡住你的全是**工程问题**。

而且仔细看,这里其实是**两类不同的缺口**叠在一起:

- 一类是**框架把能力藏起来了**:不让你配采集参数、不让你跳转到视频中段、连你打的补丁都扛不住一次升级——你想要的能力它本来有,但不给你接口。
- 一类是**输入形态本来就有好几种**:摄像头、RTSP、视频、文件夹,每种都得自己写一遍读取循环。

第一类要你**补上框架没给的配置能力**;第二类要你**把多种形态收拢成一个统一的、可一行切换的抽象**。但它们的落点是同一个:**"输入源"这个边界**。你下意识想做的,就是在这个边界上做一层属于自己的抽象——既补上配置能力,又统一形态。

> **"能跑通"和"能交付"之间,隔着一条沟。代码越廉价,你越快到达沟这边的岸,但没有任何东西会自动带你过去。**

这就是工程化的最小动作。而一个真实的项目,说到底,就是由数十个这样"该在哪里划一条边界"的决定堆叠而成。

刚才那条沟,只是它们当中最显眼的一条。

## 五、把这种"现在不管、将来必撞"的点全摊开

推理只是冰山一角。一旦你打算把这个程序从"我自己能跑"做成"别人能用、能维护、能长大",同一类问题会沿着整条链路冒出来。我们先不解决,只把它们摊在桌面上,而且**只描述问题,不开药方**:

- **代码放哪、凭什么别人 import 得到?** 你本机 `python train.py` 跑得好好的;同事 clone 下去、或者 CI 跑起来,`import` 你的模块直接报错。
- **路径怎么找?** 你代码里写死了 `"data/raw"`,换个目录、换台机器跑,全部错位。
- **原始数据、参数、产物,该怎么摆?** 原始数据被你就地改得回不去;学习率、阈值散在各处,半年后没人说得清当时用的什么;训练完一堆权重和日志散在各角落,分不清哪个来自哪一次运行——**实验复现不了。**
- **想加个新端,得动全身。** 今天只有"训练 + 推理"一个东西;你想给它配个网页 demo、或者一个桌面壳,结果发现要加进来就得把现有代码挪个遍。
- **改完不知道有没有改坏。** 你改了一处,只能靠手动点一遍来确认没出事;改十次点十次,迟早漏。
- **改一处崩三处。** 模块之间互相调用,改一个函数签名,另外两个模块跟着报错。

注意:这些里,**没有一条是"模型不够好"。** 它们全是"项目没设计好"。

而"项目设计"落到最实处,其实只有两件事:**东西放在哪(目录结构),以及谁能依赖谁(依赖边界)。**

接下来,我们就一个问题一个问题地问下去。每个问题会把我们逼到某一步——**我们不预先画目录,我们让目录被问题逼出来。**

## 六、一个一个问题,把结构逼出来

### 6.1 "我的代码,凭什么别人 import 得到?"

回到最基础的场景。你在项目根目录下 `python train.py`,一切正常。同事把仓库 clone 下去,在 `tests/` 目录里写个测试 `import` 你的模块——

```
ModuleNotFoundError: No module named ...
```

为什么你那儿能跑,他那儿不能?因为你能跑,靠的是一个**巧合**:你恰好在项目根目录启动,而 Python 默认会把"当前工作目录"加入模块搜索路径。换个目录启动,这个巧合就没了。CI 上更是必崩——CI 根本不在你那个目录跑。"本地明明能跑,一上 CI 就挂"是几乎所有人都会撞一次的经典坑,根子就在这里:**你的代码当前是靠"运气"被找到的,不是靠"约定"被找到的。**

怎么把运气换成约定?**第一步:别让代码靠"目录恰好对"被找到,把它当成一个真正会被安装的软件包来对待。** 以可编辑方式安装一次(`pip install -e .`),之后任何人、任何位置、CI、乃至未来真实用户,`import` 走的都是**同一条**路径。

但"装成包"还差一口气。设想你的包目录就摊在项目根、和你启动的位置紧挨着——这时 Python 仍可能**直接 import 到那份没经过安装的源码**,而不是你装好的那个包。你以为在测"安装后的包",其实测的是脚边那堆松散文件,"本地能跑、CI 崩"换个花样又来了。堵住它,只需把源码塞进一个专门的 `src/` 目录:有了它,你想 `import` 就**必须先安装**,本地与线上的行为从此被强制对齐。

`src/` 这一层不是多余的繁琐,它是一道闸。

> **第一个决定:把源码做成可安装的包(解决"import 靠巧合、CI 崩"),并放进 `src/`(解决"误 import 到那份没装的源码")——两个问题、两步,合成一条 `src` 布局(PyPA 官方推荐)。**

好,代码现在是个正经的包了。但这个包要干活——读数据、写日志——它第一件要搞清楚的事是:**"项目根"到底在哪儿?**

### 6.2 "项目根在哪?"—— 一个文件挪一下就崩的设计

你的代码要去读 `data/`、写 `logging/`,这些都得相对"项目根"来定位。最直觉的写法是从当前文件往上数几层:

```python
ROOT = Path(__file__).parent.parent.parent   # 数到根
```

数对了,能跑。然后你重构了一次——把这个文件从 `common/` 挪到了上一层。`parent` 的层数变了,你忘了改,于是整个项目的路径**集体错位**,而且不报错,只是悄悄写到了错的地方。

每一次目录调整都要重数一遍层数。这不是工程,是在做层级计数的算术题。**更要命的是:用 AI 帮你重构时,它最常做的就是挪文件、改结构。** 你越频繁地动代码,这种"数错层数"的事故就越频繁。

出路是:**根本别去数层数。** 在项目根放一个空的标记文件(marker file,比如 `.odp-workspace`),然后让代码从自己所在的位置**逐级向上查找**,直到遇到这个标记,所在目录即为根。文件以后怎么挪、目录怎么重构都不受影响,只要这个标记还在根上,定位就永远正确。

这是成熟工具的通用做法——`git`、`pytest`、`poetry`、`npm` 定位各自的项目根,靠的都是它(`.git`、`pyproject.toml`、`package.json` 就是各自的标记文件)。

> **第二个决定:用根目录标记文件定位项目根,代码"向上查找"而非"硬数层级"(marker-file 模式)。**

现在根能被稳定找到了。但"根下面放什么"——这是接下来、也是这篇最核心的一个问题。因为它直接决定了:这个项目将来**能不能长大**。

### 6.3 "三天后我想加个网页 demo,要把代码全挪一遍吗?"

今天,这个项目只有一样东西:一个命令行的训练 + 推理引擎。最自然的放法,就是把它直接摊在项目根下。

放之前,先想一步——**而且这一步,正是今天必须想的那一步。**

以前,"给引擎加个网页前端、再加个桌面客户端"这种事,要立项、要排期、要好几周。现在呢?你今天有了能跑的引擎,**这个周末**你大概率就会顺手让 AI 给你套一个网页:上传图片、看检测结果;再套一个桌面壳,给不会用命令行的人。**新端的出现,从"几周后的计划"变成了"几天后的冲动"。**

那么,当这个网页后端真的出现时——如果引擎是直接摊在根上的,它往哪儿放?跟引擎平级、也摊在根上?于是根目录开始堆积,越堆越乱。等你受不了、想把引擎收进一个子目录归类时,代价是:**所有 import 路径、所有文档、整套 CI,全得跟着改一遍。** 你还没开始写新功能,就先欠下一笔"破坏性重构"的债。

避开这笔债,核心只有一件事:**今天就给引擎一个具名的家**,别让它散在根上。

怎么给这个家?其实**不止一种放法**:你可以让引擎直接住进 `platform/`,将来 `web/`、`desktop/` 做根级的同级目录;也可以多打一层 `apps/`,把它们都归在底下。**两种都避开了"重排"那笔债。** 我们选后者——`apps/platform/`——是因为它顺手多做一件事:把"可独立交付的端"(apps/ 里那些)和马上要出现的"顶层共享资产"(data、models 这些)在视觉上分了层。

要说清楚:这是个**有理由的取舍,不是唯一答案**。选 `apps/` 不是因为非它不可,是因为它顺带帮我们把两类东西分开了。

也要分清:这**不是**过度设计。过度设计是为还不存在的需求**提前写代码**;而我们这里一行功能代码都没多写,只是把"东西该放在哪"提前想对了——成本是多敲一个文件夹名,几乎为零。

今天它孤零零一个,`apps/` 下就这么一个孩子,看着确实多余。但当 web、desktop 到来时,它们只是 `apps/` 下**新增的同级目录**——引擎一行代码都不用动。

> **第三个决定:给引擎一个具名的家,并加一层 `apps/` 把"端"归类;今天的引擎是 `apps/platform/`,为未来的端预留同级位置。这是有理由的取舍,不是唯一解。**
>
> 用今天的近零成本,为未来的扩展保留接缝——这是演进式架构,而非投机式实现(YAGNI 的正确用法:留接口,不预先建设)。

有了 `apps/`,一个新问题立刻冒出来:多个端开始**共用**一些东西(同一份数据、同一个权重),又各自有一些**私有**的东西(各自的日志)。这些该怎么放?

### 6.4 "数据集和权重,每个端各存一份吗?"

引擎训练出一个权重 `best.pt`。将来的网页后端要加载它做线上推理;桌面端要拿它做离线推理。它们都需要这同一个文件。

如果每个端的目录里各放一份会怎样?——多份相同的大文件,你改了一份,忘了改其余几份,迟早因不同步而出错。数据集更甚,动辄上 GB,复制多份既浪费存储,又制造一致性隐患。

所以这类"**所有端都要用同一份**"的东西——数据、模型权重、训练结果——应该提到**顶层共享**:物理上只存一份,所有端指向同一个位置。

但反过来,**日志不是这样的东西。** 训练引擎的日志(体量大、带每一轮指标)、网页后端的请求日志(每秒数百行)、桌面端的用户操作日志——它们性质各异,混在一处会让问题排查变得困难。这种"**某个端自身运行时产生的副产物**",应当留在**各自端的目录**内,谁的归谁。

**配置也归各端私有,但理由不一样**:配置描述的是"**这个端怎么跑**"——platform 的训练配置模板,和未来网页后端的服务配置,根本是两回事;它们跟着各自的端走,而不是被共享。(别因为"日志私有"就顺手把配置也归私有——它私有有它自己的道理。)

你看,同样是"该放哪",共享的要上提,私有的要下沉。这条线一画出来,目录的"分层"才第一次有了**意义**——它不再是随手堆放,而是在做一个声明:

> **第四个决定:共享资产(数据 / 模型 / 训练结果)置于顶层;端私有资产置于各端内部——日志(运行副产物)和配置(描述该端怎么跑)都归私有,各有各的理由。**
>
> 一样东西放在哪一层,等于声明"它被谁共享"——这是按"共享边界"做的关注点分离。

### 6.5 "原始数据放哪?权重又放哪?"—— 分清"输入"与"产物"

不过"放顶层共享"这条线,还能再往下追一步:同样塞在顶层 `data/` 里,所有数据真的是一回事吗?

设想你拿到一批原始数据。最顺手的做法,是直接在它上面动手:清洗、改名、删掉模糊的图、把标注格式转一下。跑通了。然后某天你想换一种清洗策略重来——却发现**原始数据已经被你改得回不去了**。

再设想另一处:你在训练前随手 `train_test_split` 一下,这次忘了固定随机种子。下次再训,验证集换了一批,两次的指标根本不可比;更糟的是,某张图这次落在 train、下次落在 test,你的"测试集"早已泄漏进训练——**你以为在测泛化,其实在测记忆。**

模型那边是同一种病:你下载的预训练权重 `yolo11n.pt`,和你自己训出来的 `best.pt`,都堆在一个 `models/` 里。过两个月,你指着一个 `.pt`,说不出它是官方的还是你训的。

这三处麻烦,根子是同一个没分清的区别:**你带进来的输入,和你生产出来的产物;不可变的原始,和可再生的派生。**

把这条线划出来,前两处麻烦就位:

- **输入 / 原始,只读,绝不就地修改**——原始数据进 `data/raw/`,任何处理都生成新副本;下载来的预训练权重进 `models/pretrained/`。
- **产物 / 派生,可再生,可以随时删了重来**——清洗、转换、划分后的数据集进 `data/processed/`;你训练产出的权重进 `models/trained/`。它们都能从"输入 + 一段确定的代码"重新生成,所以丢了不可惜。

> **第五个决定(其一):按"输入 vs 产物、原始 vs 派生"分家——`data/` 分 `raw`(只读)与 `processed`(派生),`models/` 分 `pretrained`(下载)与 `trained`(产出)。**

然后是那个常被混进来、其实是**另一件事**的问题:**train/val/test 什么时候划分?**

注意——它跟"建一个 `processed/` 目录"是**两套机制,别焊在一起**。你完全可以建好了 `processed/`,却仍然每次训练前临时 `train_test_split` 一下、还忘了固定种子;于是验证集每次都换一批,指标不可比,测试集还会泄漏。所以划分这件事,**靠的是纪律,不是目录**:它是"生成 `processed/` 的那一步"里做的事,**固定种子、一次性产出、落盘、然后冻结**;训练只去读那份固定的划分,**绝不每次临时分**。

> **第五个决定(其二):数据划分用固定种子一次性产出并冻结,训练只读那份固定划分。**
>
> 一句话记住这一节的两条:**目录分家**解决"可再生 / 不可变";**冻结划分**解决"评估可比"。有了 `processed/` 目录,**不等于**自动不泄漏——这是两条独立的纪律。

输入和产物分了家。还有几类东西既不是数据也不是权重,但同样得有自己的家。

### 6.6 "文档和测试放哪?"—— 代码之外的两类一等公民

**第一类:文档。** 你正在读的这篇、还有架构决策记录、使用说明……塞进代码注释里没人翻,丢在某个人的电脑上迟早丢。它既不是会被 `import` 的代码,也不是运行时产物,但它是项目级的一等资产。给它一个顶层的家 `docs/`,**和代码一起进版本库**——代码怎么变,它跟着一起留痕,才不会烂。

**第二类:测试。** 这一类的理由,在今天格外硬。你会拿 AI 一遍遍改这个项目——加功能、重构、替换实现。**改完,你怎么知道没改坏?**(这正是上一节问题清单里那条疼。)靠每次手动点一遍?改十次点十次,迟早漏掉一处。出路是写测试:改完一键全跑,红了立刻知道哪里坏了。而测试是**针对某个端的代码**写的,所以它属于那个端的内部、与 `src/` 平级:`apps/platform/tests/`。

> **第六个决定:文档放顶层 `docs/`(项目级、共享、随代码留存);测试放各端内部 `tests/`(端私有、与 `src/` 平级)。**
>
> 前者让"当初为什么这么做"不丢失,后者让"改了到底有没有坏"可随时验证。

不过这里要补一句,免得它将来"凭空冒出来"。还记得决定 3 给未来的端留了位置吗?等第二个端(比如网页后端)真来了,会出现一种**端内 `tests/` 装不下的测试**:"起 backend 服务,通过 HTTP 触发 platform 训练,验证两个端联动"——这种测试**不属于任何单个端**,它该有个家,在**顶层** `tests/`。

今天我们只有一个端,所以这个顶层 `tests/` 是**空的、占位的**——和 `apps/web-backend/` 一样,位置先留好,到来时才填。**今天不建它的内容,但你要知道它将来在哪。**

东西放哪,到这儿是真的理清了。还剩最后一个问题——也是最隐蔽、最要命的一个:**谁能依赖谁?**

### 6.7 "改一个地方,为什么崩三个地方?"

项目做大一点,你会有好几个业务模块:数据处理、训练、评估、推理。写着写着,它们开始**互相 import**:推理为图省事,直接 `from training import ...` 借了个函数;评估又反过来用了推理里的东西……

一开始没事,都能跑。然后有一天你改了训练里一个函数的签名——推理报错。你去修推理——评估又报错。模块之间织成了一张网,你碰任何一根线,整张网都跟着抖。

这种项目的特征是:**"能跑",但"不能动"。**

而这恰恰是今天最致命的毛病。因为你会**非常频繁地改动它**——加功能、重构、替换实现,很多时候还交给 AI 去做。**一个无法被安全改动的项目,在代码近乎免费的时代,是一种负资产**:你越想快速迭代,它崩得越频繁。

(上一节的测试,负责"改完能立刻发现坏了";这一节要解决的是另一半——**让一处改动根本波及不到其它地方**。)

怎么做?先把所有模块都要用的基础设施(路径、日志、统一的结果对象……)下沉到一个**公共基础层**;所有业务模块都只**向下**依赖这个基础层。

那业务模块**彼此之间**呢?这里有个容易讲过头的地方,得说准——**不是"彼此一条边都不许有"**。真实里"评估"本就要调用"推理"去跑出预测,这是一条正当的依赖,禁掉它你只能把推理硬塞进公共层(撑胖底座),或者重复实现一遍。所以要守的纪律不是"互不依赖",而是更准的一条:**依赖只能单向流动,不许成环(acyclic)**。评估依赖推理可以,只要推理不反过来依赖评估;你要禁的是**环**,不是所有平级的边。

把"无环"这条守住,那张网就被拆成了一棵**有向无环的树**:动一根枝子,不会牵动那些不依赖它的枝子。而入口层(`cli/`,用户敲命令的地方)天然站在最上层——它依赖下面的服务和公共层,而**没有任何东西依赖它**,所以改入口最安全。

![依赖方向:互相 import 的网 vs 只向下、单向无环的树](./image/dependency.png)

*左边模块互相依赖、连成一张网,改一处牵动全部;右边所有依赖只朝一个方向流、不成环,连成一棵树,改一处只波及"依赖它的那一支",不依赖它的纹丝不动。*

> **第七个决定:设一个公共基础层,业务模块只向下依赖它;业务模块之间允许依赖,但必须单向、不许成环(单向、无环依赖 acyclic;关注点分离)。**
>
> "东西放哪"可以靠目录画出来;但"谁依赖谁"画不出来,得靠纪律守住——这也是为什么后面写的每一段代码,都要盯着这条线做评审(review)。

七个问题,问完了。

## 七、现在,目录树自己长出来了

我们从头到尾没有画过目录。但回头看,这七个决定其实每一个都在往一张图上添一笔:

- 因为代码要能被**正确导入**(还要堵住"误 import 没装的源码")→ 它得在 `src/` 里,是个可安装的包;
- 因为根要能被**稳定定位** → 根上放一个标记文件;
- 因为要给**未来的端**留接缝、又想把"端"和"共享资产"分开 → 给引擎一个具名的家、加一层 `apps/`,引擎是 `apps/platform/`;
- 因为共享的要**上提**、私有的要**下沉** → 数据/模型/结果在顶层,日志/配置在端内(各有各的私有理由);
- 因为**输入与产物、原始与派生**必须分家、划分还要可比 → `data/` 分 `raw`/`processed`,`models/` 分 `pretrained`/`trained`,划分固定种子一次性冻结;
- 因为**文档要随代码留存、测试要随时可验证**(跨端测试另有其位)→ 顶层 `docs/`、各端 `tests/`、顶层预留一个 `tests/` 占位;
- 因为依赖只能**单向无环** → 包内设一个公共基础层,业务模块平级但只许单向、不许成环。

把这七笔叠在一起,它们拼成的,就是这棵树:

```
ODPlatform/
├── .odp-workspace              ← 根标记:代码自任意位置向上查找,遇到它即为根 (决定 2)
├── pyproject.toml              ← 仓库根:只放全仓共享的工具配置(ruff/mypy/pytest);它不是包(见下文"那两个 pyproject")
│
├── apps/                       ← 这一层把"端"归类,并为"未来的端"预留 (决定 3)
│   ├── platform/               ← 今天唯一的端:训练 + 推理引擎
│   │   ├── pyproject.toml      ← 该端自身的依赖 + 命令入口
│   │   ├── src/                ← 强制以"真实安装方式"导入 (决定 1)
│   │   │   └── od_platform/    ← 真正被 import 的包(下划线)
│   │   │       ├── common/     ← 公共基础层:各模块只向下依赖它 (决定 7)
│   │   │       ├── …/          ← 各业务子系统(平级,依赖单向、无环) (决定 7)
│   │   │       └── cli/        ← 入口层:站在依赖最上层,没人依赖它 (决定 7)
│   │   ├── tests/              ← 该端的测试:改完一键验证有没有改坏 (决定 6)
│   │   ├── configs/            ← 端私有:描述"这个端怎么跑" (决定 4)
│   │   └── logging/            ← 端私有:该端自身的运行时日志 (决定 4)
│   ├── web-backend/            ← 占位:今天空置,到来时即为 platform 的同级 (决定 3)
│   └── desktop/                ← 占位:同上
│
├── data/                       ← 共享数据 (决定 4)
│   ├── raw/                    ← 原始数据:只读,绝不就地修改 (决定 5)
│   └── processed/              ← 由 raw 生成、含固定 train/val/test 划分的数据集 (决定 5)
├── models/                     ← 共享权重 (决定 4)
│   ├── pretrained/             ← 下载来的预训练权重(输入) (决定 5)
│   └── trained/                ← 训练产出、决定长期保留的权重(产物) (决定 5)
├── runs/                       ← 每一次训练运行的完整现场:日志/曲线/检查点 (决定 4)
├── scripts/                    ← 开发期入口(装包前用 sys.path 临时桥跑 CLI);D1 落地、装包后退役 (决定 1 的配套)
├── tests/                      ← 占位:跨端测试的家,今天空置,第二个端到来时才填 (决定 6)
└── docs/                       ← 项目文档:设计、架构记录、使用说明…(随代码进版本库) (决定 6)
```

下面这张图是同一棵树的**结构视图**,颜色把它的组织逻辑标了出来——可导入的代码包、端私有、全局共享:

![ODPlatform 目录结构:代码包 / 端私有 / 全局共享](./image/structure.png)

*同一棵树换个看法:绿色=可被 import 的代码包,紫色=端私有(随端走),橙色=全局共享(顶层)。*

几个容易混的点,顺手说清:

- **包名 `od_platform` 用下划线**——因为它要能被 `import`,而 `import od-platform` 会被当成"od 减 platform",是语法错误;对外的**安装名**则是连字符的 `od-platform`(即 `pip install od-platform`)。两个名字指同一个东西,只是分属"导入层"与"安装层",各遵各的规矩。(为什么前缀是 `od_` 而不是 `odp_`,见附录 D。)
- **`runs/` 与 `models/trained/` 的分工**:`runs/` 是**每一次**训练落下的全部痕迹,数量越来越多;`models/trained/` 只放你从中**挑出来、要长期使用**的那几个权重。一个是过程现场,一个是精选成品。
- **那两个 `pyproject.toml`,以及一个端怎么用上另一个端的代码**:你会注意到顶层有一个 `pyproject.toml`,`apps/platform/` 里又有一个——它们分工不同。**顶层那个**只做一件事:放全仓共享的工具配置(代码风格、检查规则、测试发现),让 ruff / mypy / pytest 从仓库根跑时各端共用同一套规则;它本身**不是一个包**,既不放业务依赖、也不会被安装。**每个端自己那个**才是真正可安装的包,声明该端的依赖(platform 要 torch、ultralytics)和命令入口。
  那未来的 `apps/web-backend` 怎么用上 `apps/platform` 的代码?答案朴素得有点意外:**整个仓库共用同一个 Python 环境**(比如一个 conda 环境),你只要把 platform 以可编辑方式装进去一次(`pip install -e ./apps/platform`),`od_platform` 这个包就进了这个环境。之后**任何跑在同一环境里的端**——包括将来的 web-backend——一句 `from od_platform.inference import ...` 就能直接调引擎,因为它已经装在环境里,和它的源码放在哪个目录无关。web-backend 自己的 pyproject 仍会把 `od-platform` 写进依赖(把这层关系记录在案是好习惯),但让 `import` 真正生效的,是"两者装在同一个环境里"这件事,**不涉及任何打包发布**。这也是为什么决定 3 敢说"新端只是 `apps/` 下新增的同级目录,引擎一行不用动"。

如果把"目录怎么长出来的"看成一个过程,它就是下面这七步——每一步都由一个问题逼出、新增一块结构:

| 步 | 问题(为什么) | 决定 | 这一步新增 |
|---|---|---|---|
| 1 | import 不到 / CI 崩 / 误 import 没装的源码 | 做成可安装包 + `src/` 布局 | `apps/platform/src/od_platform/`、`apps/platform/pyproject.toml` |
| 2 | 项目根定位脆弱 | 根标记 | `/.odp-workspace` |
| 3 | 未来要加端,又想把"端"和共享资产分开 | 具名的家 + `apps/` 层 | `apps/`;引擎收进 `apps/platform/`;占位 `web-backend/`、`desktop/` |
| 4 | 多端共享 vs 私有 | 共享上提、私有下沉 | 顶层 `data/`、`models/`、`runs/`;端内 `configs/`、`logging/` |
| 5 | 原始 vs 派生、输入 vs 产物;划分要可比 | 分家 + 冻结划分 | `data/{raw,processed}`、`models/{pretrained,trained}` |
| 6 | 文档 / 测试放哪;跨端测试无处放 | docs 顶层、tests 端内、跨端 tests 顶层预留 | `docs/`、`apps/platform/tests/`、顶层 `tests/`(占位) |
| 7 | 改一处崩三处 | 单向无环 + 公共基础层 | `src/od_platform/common/`(+ 业务子系统平级、`cli/`) |

现在请你做一件事:**逐行看这棵树,试着指出哪一行是"因为教科书这么说"。**

你会发现一行都没有。绝大多数行后面都标着一个编号,对应着前面**一个被问题逼出来的决定**;剩下少数几行(顶层 `pyproject.toml`、`scripts/`)不是决定本身,而是**为某个决定服务的配套**——`pyproject.toml` 是决定 1"可安装包"的声明文件,`scripts/` 是装包前的临时入口(见 D1)。它们一样不是"教科书让加的",而是某个决定落地时必然带出来的脚手架。

> **这就是"设计"和"套模板"的区别:模板递给你一棵现成的树让你照着填;设计是让你先理解问题,然后树自己长出来。**

还有一点值得停一下:**这棵树今天大半是空的。** `apps/` 下面只有 `platform`,`web-backend` 与 `desktop` 是占位的空目录,顶层 `tests/` 也是空的。

空着,是对的。我们没有为任何尚不存在的需求写过一行代码,只是把"位置"提前想对了。该长出来的那天,它们自然会被填满;在那之前,空置的目录不产生任何维护成本。这就是——**为未来留好接口,但今天一分精力都不浪费。**

最后,给这套结构一个名字。一个仓库装下所有端、共享资产统一上提到顶层、各端代码靠装进同一环境直接复用——这种布局有个通用叫法:**Monorepo**(单体仓库)。与它相对的,是把每个端各自拆成独立仓库(Multi-repo)。两种都有人用、各有各的代价;为什么我们这个阶段选 Monorepo、到什么规模才该拆,是另一篇要专门掰扯的(见附录 A)。

这里你只需要记住一件事——**你不是挑了一个叫 Monorepo 的模板来套;你是被一连串问题一路推到了这个结构,事后才知道它有个名字。** 这个顺序,正是这篇从头到尾想讲的全部。

---

## 八、回到开头那个问题

我们在第三节问过:如果写出能跑的代码已经这么便宜,那真正难的、真正值钱的,究竟是什么?

现在你大概自己有答案了。

AI(或者官方文档)给你的,是"沟这边的岸"——一段能跑的代码。它**不会**告诉你:沟在哪里;该在哪条边界上做你自己的抽象;什么东西该共享、什么该私有;原始与派生该不该分家;哪个模块**不能**依赖哪个模块、哪个环必须打破;一个今天的决定会在三个月后变成资产还是债务。

这些判断,正是"工程师"与"会写代码的人"之间那条沟。

而且——**代码越廉价,这层判断就越值钱。** 当编写代码本身不再是门槛,能把代码组织成一个"可交付、可维护、可演进"的系统,就成了真正稀缺的能力。

> 程序员与工程师的差别,不在于谁掌握更多技术——而在于谁能从一件具体的小事(比如"写个检测脚本")里,看见一整套需要被构建的基础设施。

接下来一篇 **D1**,我们就把这些决定一个一个**真正落地成代码**:从一个干净的 `git init` 开始,亲手把今天纸上推演的那几堵墙——一堵一堵地**真的撞一次**,再亲手修好。今天你想明白了"为什么";D1 你会体会到"为什么"是怎么疼的。

现在你只需要记住一件事:**我们写下的每一行,都应该能回答"它解决了哪个问题"。** 答不上来的代码,就是还没想清楚。

## 边界声明:这套结构在真实生产里,到哪儿为止

在你带着这套判断力走进 D1、真正动手之前,先把这套平台的**边界**讲在明处——它不是一个能直接上生产的系统,而且**故意不是**。下面这些都是**有意的教学取舍**,不是没做完。看清它们,你才不会高估手上这套东西的成熟度。

**它是什么。** ODPlatform 是一个目标检测平台的**工程骨架 + 数据层**:项目结构、路径真相源、日志、可安装的命令行,以及后面几天要长出来的数据流水线、数据质检闸门。这些是任何真实 ML 平台都绕不开、换个任务也能复用的部分——也正是这门课要练的判断力所在。

**"多端共享"共享的是代码,不是产物。** 第六、七节我们让 `platform` / `web-backend` / `desktop` 共享同一份顶层 `data/`、`models/`,靠的是同一台机器上的文件路径。这在你的笔记本上成立。但真实企业里,对外提供推理的后端几乎一定在**另一台**机器 / 容器 / 集群上,它拿不到你训练机的本地 `models/trained/`。生产环境这层共享靠的是对象存储(S3 / OSS)、模型仓库、数据版本化——本课不涉及。**记住:Monorepo 解决的是"代码"复用,不是"产物"分发。**

**单机、单进程、串行——是按笔记本规模设计的。** 后面你写的数据处理、质检,扫盘和落盘都是串行的。几百张图零点几秒、几万张分钟级;真到几十万张、标注在网络盘上,生产系统会并行扫描、分布式落盘。本课把并发留作"知道这里要并行",不实现(后面 D4 的质检子系统会为并发留好扩展位,但不兑现)。

**训练和推理打包在同一个 `apps/platform` 里,也是有意的。** 大多数同学手上只有一台笔记本,接触不到 GPU 集群,所以这门课把"训练"和"离线推理"放进一个包、一台机器上跑通。真实企业里这两者通常是**两个独立部署单元**——训练是重的、批处理的、跑在 GPU 集群上;在线服务是低延迟、要横向扩展、要管显存的。代码放一个仓库(monorepo)没问题,但**部署边界不同**。所以更准确地说,`apps/platform` 是"训练 + 离线推理引擎",不是一个能直接对外服务的后端。

**依赖只写了下限、没有锁——复现其实只做了一半。** 你装的依赖是 `torch>=2.0`、`ultralytics>=8.0` 这种版本下限,整个仓库没有锁文件。可前面我们花了大力气讲复现:固定种子、冻结 train/val/test。这里得诚实补一句——模型能不能复现,不只看种子和划分,还看**是不是同一套依赖**:`ultralytics>=8.0` 今天装是一个版本、几个月后可能是另一个,默认行为变了,同样的数据、同样的种子也会训出不同的结果。真实平台会用锁文件(`uv.lock` / pip-tools / `conda-lock`)把整套环境钉死。本课把"锁环境"留作"知道这里要锁"、不实现;但你心里要清楚:**划分锁了、环境没锁,复现只做了一半。**

**日志写进项目目录,是教学期的便利,不是线上做法。** 本课把日志落到 `apps/platform/logging/`,纯粹是为了让你在本地直接翻、亲眼看到每一步发生了什么。真实线上服务遵循 12-factor:把日志打到 stdout / stderr,由平台(容器、日志采集器)统一收走,**不在项目树里留文件**。所以这套文件日志,搬到生产是要被换掉的——它在这里只为方便你看见过程。

**从 `git init` 到 commit,走的是单人线性节奏,没有协作那一圈。** 本课的 git 历史是"一个里程碑一个 commit、都打在 `main` 上"。真实团队靠的是分支 + Pull Request + 代码评审 + CI 卡关 + 受保护的 `main`;而且 D4 那个为 CI 设计的退出码,真要发挥作用,得有一条 CI 流水线去读它。这一整圈——分支模型、评审、把闸门接到 CI 上——是另一篇协作专题的事;本课只负责把"闸门本身为 CI 设计对"做到位。

**制品存储、实验追踪(MLflow / W&B)、分层配置**这三层,是真实平台的下一圈基础设施,本课暂不展开(后续单独讲)。

一句话:这门课教的是**地基和判断力**;地基之上,还有一整圈生产化的活在等着。把这层边界记在心里,你对这套项目的判断就不会跑偏——也更能体会,为什么前面那句"代码越廉价,判断越值钱"是真的。
