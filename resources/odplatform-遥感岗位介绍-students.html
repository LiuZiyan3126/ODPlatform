开始之前 / 先理解一件事

你扮演的,是一个真实的工程岗位

在真实的科技公司里,做一个 AI 检测系统,从来不是一个人干完所有事,而是不同岗位的人各管一块:有人专门管数据,有人专门训模型,有人专门让模型跑得快,有人专门做界面。我们这个项目,就是把这套真实的分工,搬到你们团队里。

关于"岗位"

下面五个岗位,每一个都是招聘网站上真在招的职位。你在这个项目里扮演哪个,就相当于提前体验了那份工作。做完之后,你简历上能写的不再是"会用 Python",而是"担任过 XX 工程师"。

关于"一人多岗"

如果你们组人不够 5 个,很正常——一个人身兼两个岗位就行,真实的小公司也是这样。重点是:五个职能都得有人扛起来,别漏掉任何一块。

📌 岗位 和 "模块" 是什么关系?

简单说:模块是"代码怎么分",岗位是"人怎么分工"。一个岗位通常负责 1–2 个相关的模块(因为它们本来就是一类活),另外大家还会一起维护一个公共工具层(common)。你不用记哪个模块归哪个文件夹,只要记住"我这个岗位,负责把这几件事做好"。

🧭 重要:这五个岗位,不绑定"遥感"这份数据

我们这次的练兵场是遥感目标检测,但这套岗位分工跟具体数据无关——平台和数据集本就是解耦的。换成工业质检、安防、无人机巡检……还是这五个人、这条接力链,变的只是喂进去的数据。你在这里练到的是"平台工程能力 + 团队协作",这份本事走到哪个检测领域都通用。

五个岗位 / 看看哪个是你

团队里的五个人

读下面五张卡片,看看哪个最适合你、或者你被分到了哪个。每张卡片都告诉你:这个岗位干什么、你具体负责哪几块、你和谁交接、要注意什么。

01
数据工程师
Data Engineer
数据工程师数据质量Data Engineer

你是干什么的

你是整个团队的"数据守门人"。模型再厉害,数据是脏的也白搭。你负责把原始数据整理干净、转成标准格式,并在训练前把所有数据质量问题揪出来。一句话:数据靠不靠谱,你说了算。

你具体负责这几块

数据流水线 数据验证 和大家共管 common
  • 把原始标注数据转成 YOLO 格式,切分训练/验证集
  • 生成数据配置清单(data.yaml)
  • 写质检:检查图片标注配对、坐标合法、类别正确
  • 出一份清晰的数据质量报告

你和谁交接

↓ 你交给算法工程师:通过质检的、标准格式的数据集 + data.yaml。他拿到才能开始训练。
⚠ 注意:你在整条链的最上游,你慢了大家都得等。所以尽早交出一个能用的小数据集,让队友先动起来,别等全部完美了才交。

你会练到的技能

Python数据格式处理数据校验OpenCV
02
算法工程师
ML / Algorithm Engineer
算法工程师ML EngineerCV 算法

你是干什么的

你是"模型的炼丹师"。整个项目的"智能"从你这来。你负责训练模型、调参数、做评估,用客观数字证明这个模型到底行不行。一句话:模型效果好不好,你负责。

你具体负责这几块

训练 评估 运行配置(你主要的调参阵地)
  • 组织训练流程,支持断点续训
  • 调超参数(都在配置文件里,不动代码)
  • 训练完归档最好的权重(best.pt)+ 记录实验
  • 算 mAP、精确率、召回率,评估模型好坏

你和谁交接

↑ 你等数据工程师:他给你干净的数据集,你才能开训。
↓ 你交给推理工程师:训练好、评估达标的 best.pt 权重 + 类别信息。
⚠ 注意:交模型给推理工程师时,一定要把"你训练时怎么预处理图片的"讲清楚(图片缩放、归一化等)。不然他那边推理结果会对不上,两人会互相找半天 bug。

你会练到的技能

PyTorchYOLO 原理超参调优指标评估
03
推理工程师
MLOps / Inference Engineer · 全项目最硬核
推理工程师MLOps Engineer模型部署后端

你是干什么的

你是"让模型真正跑起来的人"。算法工程师训出的模型,在他电脑里只是个文件;是你把它变成一个能实时、高速、稳定运行的服务。这是全项目技术含量最高的部分——也是最酷的。一句话:模型跑得快不快、稳不稳,你负责。

你具体负责这几块

推理(多线程流水线) 帧源 frame_source 共管 common(性能/日志)
  • 搭四级多线程流水线(读帧→推理→画框→输出)
  • 做性能优化,把帧率从卡顿拉到 60+ FPS
  • 设计稳定的接口,让界面能接进来
  • 处理摄像头/视频/网络流等各种输入源

你和谁交接

↑ 你等算法工程师:他给你 best.pt 权重,你装进流水线。
↓ 你交给应用工程师:一个能调用的推理引擎(InferService)。
⚠ 注意:你的输出接口,应用工程师的界面要靠它。接口先和他约定好、尽量别随便改——你一改,他界面就崩,会很影响进度。

你会练到的技能

多线程/并发性能优化服务化设计OpenCV
04
应用工程师
Application / Frontend Engineer · 做出能看见的东西
应用工程师前端/客户端软件开发

你是干什么的

你是"把引擎变成产品的人"。前面几个岗位做的都是"看不见的内核",而你做的是用户真正能打开、能看、能点的界面。检测结果好不好看、用起来顺不顺,全看你。一句话:最终的体验,你负责。

你具体负责这几块

可视化(画框画标签) 桌面端界面 使用帧源模块
  • 把检测结果画成漂亮的框 + 中英文标签
  • 做桌面端窗口,显示实时检测画面
  • 把推理引擎接到界面上,处理实时数据流
  • 做交互细节(实时显示、暂停、状态反馈)

你和谁交接

↑ 你等推理工程师:他给你一个能调用的推理引擎,你把它接到界面。
⚠ 注意:你的界面依赖推理工程师的接口。早点和他确认接口长什么样,这样他改内部优化时不影响你,你俩能各干各的、互不卡。

你会练到的技能

PyQt/GUI可视化OpenCV 绘制界面交互
05
架构师 / 技术负责人
Architect / Tech Lead · 把大家焊成一个系统的人
架构师Tech Lead技术负责人兼项目统筹

你是干什么的

你不属于某一个模块,你管的是"整体"。其他四个人各做各的,谁来保证他们能拼到一起、不互相打架?是你。你定整个项目的结构、维护大家共用的工具、做 code review、当协作冲突的"裁判"。一句话:整个系统能不能协同运转,你负责。

你具体负责这几块

公共工具层 common(你主导) 整体架构 代码规范 & review
  • 搭好项目骨架(目录结构、模块怎么分)
  • 维护 common:路径、日志、结果封装等公共工具
  • 统一代码规范,review 大家的代码
  • 当各岗位接口对不上时,拍板决定怎么改
  • (通常还兼)推进进度、统筹答辩

你和谁协作

↔ 你和所有人:你定的公共工具和项目结构,是其他四个岗位协作的"地基"。你是把团队焊成一个整体的人。
⚠ 注意:common 是大家都在用的,谁要改 common 都得先经过你。否则一个人随手一改,可能让其他三个人的代码全报错。你是公共代码的守门人。

怎么分工 / 看你们组几个人

你们组几个人?这样分

五个岗位,但你们可能没那么多人。下面给三种情况的分法。核心原则:五个职能都得有人扛,人不够就一人兼两个。

4 个人
  • ① 数据工程师
  • ② 算法工程师
  • ③ 推理工程师
  • ④ 应用工程师
    + 兼架构/统筹

架构这一摊,由组里最懂全局的人兼着。

5 个人 ★ 最理想
  • ① 数据工程师
  • ② 算法工程师
  • ③ 推理工程师
  • ④ 应用工程师
  • ⑤ 架构师 / Lead

一人一岗,职责最清楚。

6 个人
  • ① 数据工程师
  • ② 算法工程师
  • ③ 推理工程师 A
    流水线核心
  • ④ 推理工程师 B
    帧源 + 性能
  • ⑤ 应用工程师
  • ⑥ 架构师 / Lead

推理最难,人多就拆两个人做。

你们怎么配合 / 一场接力

记住这条线:谁交给谁什么

你们五个不是各干各的,而是一条接力链。每个人把自己的"产出"交给下一个人。看懂这条线,你就知道自己卡住会影响谁、自己在等谁。

数据 → 算法

数据工程师交出通过质检的标准数据集 + data.yaml。算法工程师拿到它才能开训。

算法 → 推理

算法工程师交出达标的 best.pt + 类别信息 + 预处理口径。推理工程师装进流水线。

推理 → 应用

推理工程师交出一个能调用的推理引擎(稳定接口)。应用工程师接到界面上。

🏗 架构师:不在接力棒上,在接力棒下面

四棒往右传,架构师在底层托着所有人——搭骨架、维护 common、统一规范、review 代码、当接口对不上时拍板。没有他,四个人各写各的,迟早拼不到一起。

🤝 配合的两条小建议(很有用)

① 先约定接口,再各自开工。动手前,相邻两个岗位先碰一下:"我交给你的东西长什么样?"约定好了再写,能省下大量返工。
② 早点拼到一起。别等各自全做完才合并——第一周就用假数据/小模型把整条链路打通,后面再慢慢替换成真的。这样集成时不会手忙脚乱。
